XBA2DE Performance Audit

The algorithm was correct but unusable on the large datasets it was designed for. Ninety-eight percent of training time turned out to be one function walking tensors one element at a time.

BayesNet 1.3.0

Result

Five implementation defects fixed. No change to any model produced.

223× Pair ranking. SelectKPairs, the boosting loop's per-round cost, at n=40 / m=20 000.
397× Model fitting. A single XSp2de fit, at n=80 / m=5 000.
67× End-to-end. A complete XBA2DE fit, identical ensemble, identical accuracy.

At the scale XBA2DE was built for — 100 features, 100 000 samples — one pair ranking took roughly 34 minutes before and takes 9.7 seconds now. A complete fit on that dataset now finishes in 42 seconds. The same run before the fixes projects to about two and a half hours.

Every change is an implementation fix: the arithmetic is unchanged, and in most cases the operands are evaluated in the same order, so the scores are bit-for-bit identical. The remaining barrier is algorithmic and is described at the end.

Where the time went

Training the ensemble was never the cost. Ranking candidate pairs was.

XBA2DE's boosting loop calls Metrics::SelectKPairs once per round to re-rank all n(n−1)/2 variable pairs under the current sample weights, then consumes k = 2^tolerance of them — usually one. On a deliberately small case, n=40 and m=5 000, the split was stark:

Timing the four information-theoretic kernels that every pair score is assembled from located the cause precisely. One of them is two orders of magnitude slower than a sibling that does strictly more work:

Both slow kernels route through the same place: the two-argument Metrics::conditionalEntropy, which indexed the tensors value by value. Each secondFeature[i].item<int>() is an ATen dispatch — four of them per sample, on a function called O(n²) times per boosting round.

Findings

Ordered by measured cost. H — dominant cost or scaling hazard. M — smaller or latent.

H1

Two-argument conditionalEntropy indexed tensors element by elementfixed

Four ATen dispatches per sample where the three-argument sibling used raw accessors, making it ~50× slower while doing less work. This single function was ~99 % of the pair ranking, and the pair ranking was ~98 % of training.

Rewritten with a dense (X,Y) count table read through accessors. Cells that never occur are tracked explicitly, so the zero-probability branch behaves exactly as the nested maps did.

bayesnet/utils/BayesMetrics.cc:189
H2

Per-feature marginals recomputed inside the pair loopfixed

Three of the four quantities in each pair score — I(Xi;C), H(Xi|C) and H(Xi) — depend on one variable only, yet were recalculated for every pair, i.e. n−1 times each. Hoisting them turns that part of the ranking from O(n²·m) into O(n·m), leaving only the genuinely pairwise terms in the inner loop.

bayesnet/utils/BayesMetrics.cc:33 — SelectKPairs
H3

A full O(n²·m) ranking is recomputed for every model addedopen

SelectKPairs sits inside the boosting while loop. It ranks every pair, then consumes k = 2^tolerance of them — typically one. In a traced run, 16 models were built and 15 discarded by the convergence check, each round paying the full ranking.

This is correct by design, since the weights change every round, and it is the barrier that remains after H1 and H2. Fixing it means changing the algorithm — incremental or lazy re-ranking, a refreshed top-K, or pair sampling — which is a research decision, not a cleanup.

bayesnet/ensembles/XBA2DE.cc:88
H4

XSp2de::trainModel repeated the same antipatternfixed

dataset[f][i].item<int>() executed m×n times per fit — 3.9 s per model at n=100 / m=80 000, and the boosting loop refits a model every round. Now read through a 2-D accessor with a reused instance buffer. The single-superparent sibling XSpode carried the identical bug and was fixed with it, which also benefits XBAODE and XA1DE.

bayesnet/classifiers/XSP2DE.cc:141 · bayesnet/classifiers/XSPODE.cc:112
H5

Batch prediction copied the whole test set into every worker threadfixed

threads.emplace_back(worker, test_data, …) passes by value: with chunk_size capped at 150, that is m/150 copies of the entire test matrix, O(m²·n) bytes. At m=100 000 and n=100 it amounts to roughly 26 GB of memcpy per prediction. The fix is std::cref; the worker already took a const reference and the data outlives the joins.

Present at five call sites across four files, all corrected.

XSP2DE.cc:466 · XSPODE.cc:344 · XA2DE.cc:91 · ExpClf.cc:61,122
M1

Dead train/test copies materialised on every fitfixed

X_train_, y_train_, X_test_ and y_test_ were built with TensorUtils::to_matrix at the top of trainModel and never read — the loop works on the tensors directly. O(n·m) of copying discarded per fit. Members removed; XBAODE keeps its own because it genuinely uses them.

bayesnet/ensembles/XBA2DE.cc:59 · XBA2DE.h:26
M2

The convergence check re-predicts with the entire ensemble each roundopen

Cost grows as O(n_models²) over a run. Now that H5 has removed the copy overhead this is no longer visible at the sizes measured, but it remains the next scaling limit after H3 for runs that build many models. Caching per-model validation predictions would make it linear.

bayesnet/ensembles/XBA2DE.cc:118
M3

Child-table denominator re-summed for every cellfixed

computeProbabilities recomputed N(sp1,sp2,c) inside the childVal loop although it does not depend on it, making the pass O(fCard²). Hoisted out; the summation order per class is unchanged, so the probabilities are bit-identical.

bayesnet/classifiers/XSP2DE.cc:322
M4

Training status is reported as WARNING on almost every runnot changed

The note "Pairs not used in train: N" and the accompanying status = WARNING fire whenever any pair remains unconsumed, which is nearly always true by construction. The status field therefore carries no signal. Left alone deliberately — changing it alters reported behaviour, which is outside a no-semantic-change batch.

bayesnet/ensembles/XBA2DE.cc:167
M5

Head-truncation erased one element at a timefixed

The ascending branch of the top-K cut called erase(begin()) in a loop, O(P²) in the number of pairs. Replaced with a single range erase.

bayesnet/utils/BayesMetrics.cc:82
M6

Weight total accumulated through a float narrowingfixed

totalWeight += weights[i].item<float>() narrowed each float64 weight to single precision on the line after the joint counts read the same value as a double. Corrected as part of H1; this is the one change that can move a result, and only in the last few bits.

That fit converged after 2 models, so its ranking share is unrepresentative — the synthetic generator makes the problem too easy at this size. On real data with more boosting rounds, each additional round still costs a further 9.7 seconds of ranking. That is H3, and it is now essentially the entire cost of training.

How this was verified

Every change was measured and checked against invariants, one step at a time.

A profiler was built first and a baseline recorded before any code was touched. Each fix was then applied, rebuilt, and re-measured against that baseline. Alongside the timings the harness records the ensemble's accuracy and model count, and compare.py fails loudly if either moves. Across all five configurations, accuracy matched to the last bit of the double and the model counts were identical.

And against the test suite

tests/TestUtils.cc was subsequently ported to the arff-files 2.x API, so the unit tests build and run again. Two independent results came out of it.

First, the suite was run twice — once with the performance changes applied and once with them stashed — and produced identical results: 94 test cases passing and 40 failing in both runs, with the same distribution across files. The optimizations move nothing the tests can observe.

Second, the categories that directly exercise the rewritten code all pass in full: Metrics (170 assertions, covering conditionalEntropy, mutualInformation and SelectKPairs), FeatureSelection (225), Network (301), Classifier (34), Node, MST, A2DE, XA1DE, XA2DE and XSPnDE. Those are recorded expectations, not synthetic invariants.

The 40 remaining failures are dependency drift, not this work

Conan is resolving major versions the project does not declare: folding 2.0.0 against a pinned 1.1.2, and fimdlp 3.0.0 against a pinned 2.1.3. The pinned releases are not in the local cache at all, so the build silently took the newer ones.

folding 2.0.0 changed how a seed maps to folds — its own README says so, and a direct comparison confirms it: for the same 150-sample stratified problem with seed 271, fold 0 selects a completely different test set under 1.1.3 than under 2.0.0. Every recorded score in the suite was produced on the old split, so every score assertion that goes through raw.X_test now misses.

Resolving it is a reproducibility decision: pin folding/1.1.3 and fimdlp/2.1.3 — both are available on the Cimmeria remote — or re-record the expectations against the new majors and accept that older published results no longer reproduce.

One genuine test bug was fixed along the way: ACTUAL_VERSION in TestBayesModels.cc was the literal "1.2.3", stale since the 1.3.0 bump and failing for every classifier. It now reads the version CMake configures into bayesnet/config.h.

Reproducing it

cmake -S . -B build_Release -DENABLE_BENCHMARK=ON
cmake --build build_Release --target xba2de_profile --parallel

benchmark/xba2de_profile/run.sh baseline     # record
# ... change code, rebuild ...
benchmark/xba2de_profile/run.sh candidate    # record again
benchmark/xba2de_profile/compare.py \
    benchmark/xba2de_profile/results/baseline.json \
    benchmark/xba2de_profile/results/candidate.json

The profiler is self-contained and generates its own fixed-seed synthetic data, so it builds and runs while the ARFF loader is broken.

What comes next

The implementation is no longer the bottleneck. The algorithm is.

With H1, H2, H4 and H5 in place, a full pair ranking at target scale costs about ten seconds and the rest of a boosting round costs almost nothing. Training time is now, very nearly, the number of rounds times the cost of one ranking. Three directions, in increasing order of how much they change the method:

  • Refresh the ranking every T rounds rather than every round, accepting slightly stale weights. Cheapest to try, and the effect on accuracy is directly measurable with the existing harness.
  • Maintain a top-K frontier and re-score only its members plus a sample of the rest, since the loop consumes one pair per round but ranks thousands.
  • Incremental re-scoring, exploiting the fact that AdaBoost's weight update touches only the sign structure of the previous round's errors.

Two smaller items also remain open: M2, the quadratic convergence check, and M4, the status field that always reports a warning.
